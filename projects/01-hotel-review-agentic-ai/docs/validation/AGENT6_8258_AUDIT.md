## 8,258개의 의미

8,258개는 호텔 수준의 독립적인 우선과제 수가 아니다. 처리 구조는 다음과 같다.

`리뷰 1개 → 문제 label 여러 개 → label마다 Agent 5 impact 1개 → impact마다 Agent 6 action 4~10개`

Agent 6 스키마와 프롬프트에는 action 수 상한이 없었고, “필요한 모든 materially distinct action”을 내도록 되어 있었다. 그 결과 1,321개의 매우 세분된 리뷰-level impact 각각에 평균 6.25개 조치가 생성되었다.

## literal 중복과 semantic 중복

공백·대소문자를 정규화한 action 문장을 비교했을 때 정확히 같은 문장은 없었다. 8,258개 모두 문구 자체는 달랐다. 그러나 이것이 8,258개의 독립적인 전략을 뜻하지는 않는다.

- 각 호출이 단일 리뷰 근거에 맞춰 문구·KPI·담당자를 다시 작성한다.
- 같은 호텔의 같은 Feature/Journey 문제도 리뷰 label별로 별도 호출한다.
- 교육, 표준작업절차, 안내문, 체크리스트, 모니터링 같은 실질적으로 유사한 조치가 다른 문장으로 반복될 수 있다.
- 기존 파이프라인에는 호텔×Feature×Journey 수준 semantic clustering이나 action consolidation 단계가 없었다.

즉 **literal duplicate는 0이지만, 의사결정 수준의 중복은 구조적으로 많다.** 이번 IPA 후처리가 필요한 이유다.

## 현재 논문용 압축 결과

기존 8,258개를 버리지 않고 다음 방식으로 재사용했다.

1. 호텔별 IPA에서 안정 Q2를 선별한다.
2. 안정 Q2 호텔×Feature×Journey 15개 그룹과 일치하는 기존 action을 찾는다.
3. 근거 적합성을 기준으로 그룹당 2개만 선택한다.
4. 15개 그룹 × 2개 = 30개 action으로 압축한다.
5. 교수 보고용으로 호텔별 최상위 1개씩 5개 핵심 우선과제를 별도 정리한다.

| 압축 단계 | 결과 |
|---|---:|
| 원시 Agent 6 후보 | 8,258 |
| 안정 Q2 그룹 | 15 |
| 기존 후보 중 최종 연결 action | 30 |
| 안정 Q2 해당 호텔 | 5 |
| 교수 보고용 호텔별 최상위 과제 | 5 |

이 압축에는 신규 API 호출이 없었다. `stable_q2_existing_agent6_actions.csv`가 30개 연결 결과이고, `professor_top_priority_by_hotel.csv`가 교수 보고용 5개 최상위 과제다.

## 코드 수정 판단

앞으로 Agent 6를 1,321개 impact에 다시 호출하면 같은 과잉 생성이 반복된다. 수정한 코드는 다음 두 경로를 모두 보존한다.

- 기본 모드: 과거와 동일하게 모든 impact 처리
- 우선순위 모드: 안정 Q2 호텔×Feature×Journey만 1회 호출하고 그룹당 최대 2개 action 생성

현재 데이터에는 신규 Agent 6 호출보다 기존 8,258개에서 선별한 30개를 사용하는 무과금 경로가 우선이다.
